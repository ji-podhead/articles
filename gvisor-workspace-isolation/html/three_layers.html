GET 3000-ws-abc123x.platform.example - the URL encodes both the target port and the workspace; the app keeps running on its natural port inside its own container, untouched.

LAYER C · Identity Proxy (the bouncer)
Terminates TLS · verifies the session/JWT · looks up an in-memory table workspace_id → {ownerID, backendIP} · forwards only if the requester's identity matches the workspace's owner. No raw port is ever published on the internet.
Blind spot: anything a legitimate, authenticated user does once inside their own workspace - that east-west traffic never crosses the front door.
↓ inside the tenant's own segment
LAYER B · VLAN / ipvlan (the soundproof wall)
Every tenant's frames are 802.1Q-tagged on their own sub-interface (ip link add link eth0 name eth0.102 type vlan id 102, then a macvlan/ipvlan Docker network - never the default bridge). Isolation is enforced in the kernel's frame-forwarding path, before any firewall rule is even consulted.
Blind spot: the host kernel itself - an attacker who breaks out of an unsandboxed container lands as root on the bare host, and one ip link command undoes every VLAN you configured.
↓
LAYER A · gVisor (the straitjacket)
Application syscalls never reach the real host kernel - the Sentry emulates them in a Go userspace process (see the architecture diagram above). A Sentry escape is a far rarer problem than a routine kernel CVE.
Blind spot: the local network - gVisor still hands ordinary frames to whatever Docker network it is attached to, and a sandboxed app can freely scan an unsegmented bridge.
Each layer's blind spot is precisely the next layer's job
That is the whole argument for running all three together - plus the fourth gate nobody puts in the diagram: an egress allowlist, default-deny outbound per workspace, which gates what a workload can send out. Identity gates who comes in, VLANs gate local reach, gVisor gates the kernel - none of them say anything about your own container quietly uploading data to an attacker's server.
