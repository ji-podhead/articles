What actually happens inside gVisor when your app makes a syscall

Figure 1 · The application never talks to the real host kernel - every arrow here is the redirection that guarantees it.
UNTRUSTED USER SPACE
App process (e.g. a Node.js server) fires a syscall: open() read() socket() send()
↓ intercepted before the host kernel ever sees it
INTERCEPTION - the syscall never leaves userspace
Systrap, the default and fastest path as of 2026: lightweight per-CPU stub processes trap the instruction and hand it to the Sentry over a shared-memory queue · KVM: the Sentry becomes a lightweight hypervisor via /dev/kvm, intercepting at the hardware-instruction level
TRUSTED USER SPACE - THE gVISOR SANDBOX, ONE PER CONTAINER
Sentry - the Go userspace kernel
A single Go process per sandbox implementing the Linux syscall surface: 300+ syscalls emulated in memory. When your app calls open(), the Sentry answers - not the host.
Netstack is embedded, not a separate process: a full TCP/IP stack as a Go library inside the Sentry, building real L2/L3 packets before anything reaches the host's network hardware.
→LISAFS protocol over a
shared-memory ring buffer
(replaced the old 9P protocol)
Gofer - one separate process per container
Owns the real filesystem: the sandbox's own mount namespace is empty - the Sentry has no path to the host FS unless the Gofer explicitly hands it something.
Directfs (the modern default): the Gofer donates specific file descriptors for the mounts it approves; the sandbox then uses ordinary FD-based syscalls (openat, fchownat) on those handles only, with O_NOFOLLOW enforced via seccomp to stop symlink tricks.
All writes land in a writable tmpfs overlay - the underlying container image is never modified, and containers restart clean.
Both processes are seccomp-bpf caged
Sentry: only network and memory syscalls reach the real host kernel · Gofer: only file read/write on handles it has already validated.
PRIVILEGED SYSTEM SPACE - the real Linux host kernel
Only the two narrow, pre-approved paths above ever touch this box. A sandbox escape means exploiting the Sentry's own Go implementation of a syscall - a real but far rarer engineering problem than a routine kernel CVE.
