Browser agents: a real CVE, and the mitigation that actually works

"The Hidden Dangers of Browsing AI Agents", Mudryi, Chaklosh, Wójcik (ARIMLABS.AI), arXiv 2505.13076
CVE-2025-47241 (CVSS 9.3, Critical), a domain allowlist that trusts its own URL parsing
Browser Use's allowlist check split a URL on ":" and compared the result against an operator-configured allowlist, it never accounted for HTTP Basic Auth syntax.
https://example.com:pass@localhost:8080
"example.com" is a USERNAME here, not the hostname
→
Agent believes: "example.com" (allowed) ✓
Real destination: localhost:8080 (never allowed)
The agent's own belief about its boundary was wrong, and it had no way to know. A textbook SSRF enabler, combined with the prompt-injection bug below, a path to full agent hijacking. Fixed upstream in v0.1.45. This is application-level trust in the agent's own URL parsing, exactly the class of check that a network-layer, default-deny egress firewall makes irrelevant regardless of any parsing bug inside the container.
Mitigation effectiveness, as reported in the paper's own benchmarks
No defense (base rate)
~25% attack success
LLM-based injection detector
~8% attack success, better, not solved
Planner/executor isolation
0% attack success, the only mitigation that reaches this
Why planner/executor isolation wins, and the direct line to a tool-call gateway
A PLANNER component only ever sees trusted, pre-vetted input and makes decisions. A separate EXECUTOR component is the only one that touches untrusted content (the raw page HTML) and holds actual tool/browser privilege. A security monitor enforces that untrusted data can never flow back into the planner's own reasoning, the decision-maker never sees what the attacker controls.
This is architecturally the same shape a well-built tool-call gateway should take: the capability decision happens BEFORE the agent.s container executes anything, evaluated against server-side policy the agent's own output cannot influence, the planner/executor split, just for tool calls instead of a DOM.
The field is still building this out, but the best-known answer is an architecture choice, not a bolt-on filter.
