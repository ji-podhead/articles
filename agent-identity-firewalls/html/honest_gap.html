Check your own system: a scoping field that is written, but never read

Found in our own gateway's secrets store during the audit for this piece
WRITE TIME: this part is real
A per-agent access-control field is written on every secret creation, and every token mint records which agent it was minted for. The data model for per-agent scoping exists.
≠
READ TIME: never checked
The secret lookup does not filter by the per-agent field at all. Token validation checks name, revocation, expiry, never the agent binding. Any caller holding a valid token for that secret name can read it, whatever the field says.
Practical consequence
Scoping on paper, decorative in practice. Mitigated only by the identity chain in front of the store, so not a wide-open hole, but real.
Why this is the good kind of finding
The verified identity already flows through every other code path. The fix is two functions consuming a field that already exists: small, surgical, cheap to close.
The five-minute audit for your own stack
Does a per-agent access-control field in your secrets store get checked at read time, or only written at creation? A data model that looks right and a decision path that consults it are two different claims, and the gap between them is where "we thought we had this" lives.
A gap with an existing data model is cheap to close. Flagged, not fixed silently.
