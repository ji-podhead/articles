A worked example: a per-agent scoping field that is written, but never checked

WRITE TIME: this part is real
A per-agent access-control field is written on
every secret creation and update.
Every access token records which agent
it was minted for.
≠
ACCESS TIME: never checked
The secret lookup does not filter by the
per-agent field at all.
Token validation checks name, revocation,
expiry, never the agent binding.
Practical consequence
If a per-user OAuth token for a connected inbox were stored today, scoping it to one agent via that field would be purely decorative.
Any caller holding a valid token for that secret NAME can read it, whatever the field says.
Mitigating factor: reaching the store at all still requires passing the gateway identity chain first. This is not a wide-open hole.
Why this is the good kind of finding
The data model for per-agent scoping already exists. This is a couple of missing comparisons in two functions, not a missing architecture: the verified identity already flows through every other code path in the system (the gateway diagram above). The store's own checks simply are not consuming it yet. Fixing it is small and surgical, precisely because everything else was built right.
Flagged, not fixed silently. That is what shipping honest gaps instead of hiding them looks like in practice.
