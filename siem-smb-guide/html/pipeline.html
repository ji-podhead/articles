How a SIEM actually works: the seven stages

The same seven stages whether you host it yourself or rent them from a cloud provider - the alert is the output, not the feature.
1 · COLLECT - EVERY LOG SOURCE YOU POINT AT IT
Logs
app · proxy · platform
Network
flow records · IDS alerts
Identity
auth events · API audit
Runtime
syscalls via eBPF sensors
Posture
IaC scans · config state
↓ normalize into one schema
2 · NORMALIZE
One schema: OCSF / ASFF - or your own
A firewall drop, a web-server access log and a Suricata alert share no schema by default. Detection rules and ML models only compose across sources once everything has the same shape - normalization is the hard part, not detection.
3 + 4 · DETECT
3 · Rules
signatures · regex · file-integrity checks · allowlist violations
4 · ML / behavior
baselines · anomaly scores - every finding carries confidence + model_version
5 · CORRELATE + ATTRIBUTE
Chained events become one incident
"A dropped connection happened" is nothing. "Container checkout-api, three seconds after an unusual outbound connection, followed by a shell spawned inside the same container" is an incident. If the pipeline cannot chain events back to one workload, it collects logs - it does not detect threats.
6 · ALERT - A RANKED TRIAGE QUEUE, NOT A WALL OF RED
Risk score ranks the queue, a human decides
Risk Score = Exposure × Privilege × Data Sensitivity × Exploitability × Confidence
Weights are configurable per workload - a payments service weights PCI-relevant findings much higher than a marketing site.
7 · RESPOND + RETAIN
Block, isolate, revoke - and keep the evidence
Containment now, plus long-term retention: the store the investigation comes back to.
A SIEM is not a scanner and not an alert generator. It is a correlate-and-retain engine over every log source you point at it.
