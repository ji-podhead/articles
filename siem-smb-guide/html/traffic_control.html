Controlling traffic: ports, IP allowlists, and the WAF layer

Two layers, two different jobs - the firewall decides who gets to knock, the WAF decides which knocks look malicious.
Client / Internet
bots · scanners · users - plus the traffic you invited and the port you forgot you opened. Every knock is a log line waiting to happen.
→
Edge: firewall + WAF
Firewall
default-deny · only required ports open (443) · admin ports behind a source-IP allowlist
WAF
OWASP CRS patterns (SQLi, XSS, path traversal) · rate limits · geo/IP blocking
→allowed
Application / gateway
identity check on minted sessions · payload inspection · per-user rate limits - the only point guaranteed to see fully decrypted, parsed content
→
Backend
answers only to allowlisted upstreams - everything else is egress-dropped. The blast radius of a compromised pod stays this small.
↓ rejected traffic
Blocked - and logged
A rejected connection is a log entry, never a silent drop: which ports were probed, from where, how often. Exactly the data an investigation wants.
The Docker NAT pitfall
A published container port routes around host firewall front-ends via the nat table - the UI says "blocked", the port is open. Verify actual reachability: ss -tlnp vs docker ps, not the firewall config.
Self-hosted: nftables/ufw + Coraza or ModSecurity (OWASP CRS)
AWS: Security Groups + NACLs + AWS WAF & Shield
