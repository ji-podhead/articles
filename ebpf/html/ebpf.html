The kernel-level pattern in four steps

eBPF: small, verified, sandboxed programs inside the kernel - programmable hooks, no app changes, no restarts.
1 · Uprobes on SSL_write / SSL_read
Attach to the crypto library's symbols. There - before TLS encryption - the prompt exists as plaintext in process memory. "Zero instrumentation": you don't touch the app; the kernel does the tapping.
→
2 · Ring buffer transport
The captured plaintext is streamed to a userspace daemon via an eBPF ring buffer - kernel events handed over without polling.
→
3 · A small classifier, not an 8B judge
No ML in the kernel - eBPF programs run in a verified VM with loop limits. Instead: a 22M-86M prompt-guard model in a Rust/C++ sidecar, or embeddings + XGBoost, sub-millisecond.
→
4 · Verdict back via eBPF map
The verdict lands in kernel memory the packet path reads - drop, TCP-RST, or freeze the offending process.
The honest limits
Uprobes bind to library symbols - Go's inlined crypto/tls, rustls and custom TLS stacks break "zero instrumentation" · streamed prompts must be reassembled in userspace anyway (eBPF reads only a few KB per invocation) · eBPF doesn't run inside gVisor - the sensor watches from the outside · kernel enforcement is fail-closed by definition: if your posture demands fail-open, the verdict belongs in a threat event, not in a kernel map.
