The landscape: static scheduler vs learning economy

Figure 2 · The trade: LiteLLM is a battle-tested scheduler with static policy; the JiMesh router is a smaller machine that learns two things static strategies cannot express - that evidence decays, and that failures have prices.
ASPECTLITELLM ROUTER (STATIC POLICY)JIMESH ROUTER (LEARNING ECONOMY)
Selectionweighted shuffle (rpm/tpm), least-busy, latency-, usage-, cost-based strategiesdecayed per-model posteriors + exploration, blended 0.7×bandit + 0.3×user preference
429 responseimmediate cooldown, 5 seconds default - same for free and paid deploymentscost-scaled: free 5s · <$0.50 30s · <$3.00 60s · $3.00+ 5 min; 402 → 24h bench (only extends, never shortens)
Quota knowledgerpm/tpm limits you configure yourself; headers not parsed into a quota modelx-ratelimit-* parsed per vendor with confidence model + shared-pool inference
Free vs paidorder/priority parameters per deployment - the operator must encode the preferencefree-first failover as ordering principle: a paid key is never picked while a free key is healthy
State & maturitybattle-tested, Redis-shared across instances, mature per-error retry policies and fallbackslearns provider drift via decay; in-memory state (a restart re-learns - an honest limit)
Sources: LiteLLM - docs.litellm.ai/docs/routing (verified Sep 8, 2026) · JiMesh - internal/router + internal/keypool + internal/quota. LiteLLM's fallbacks, retry policies and per-error-type cooldowns are more mature than anything here; what the static approach cannot do is make the 429 on a free key and the 429 on a paid key mean different things.
