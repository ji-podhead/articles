Two ingestion processes, one synthesis engine

The same architecture holds two very different intake paths: a curated knowledge base built once, and cheap schema-driven instance ingestion repeated for every document.
Process A - building the knowledge base
Unstructured expert knowledge: textbooks, guidelines, studies. Expensive once, LLM-intensive, reused forever.
Intelligent chunking along semantic boundaries
Entity extraction per chunk
Relevance reranking to filter the junk
Embedding + storage of the high-value remainder
→ collection: medical_knowledge / technical_manuals
Process B - ingesting instance data
A single document: a discharge letter, a maintenance log, a lab report. Cheap per document, schema-driven, repeatable.
Classification + metadata extraction against the ontology schema - patient_id, document_type, date. No open-ended entity extraction.
Simple chunking
Embedding + storage together with the rich payload
→ collection: patients_data / building_documents
↓ precise, filtered queries against instance data + deep context from the knowledge base
RAG is the synthesis engine between the two
The expensive investment in A is what makes every cheap document in B retrievable with surgical precision. Payloads - patient_id · document_type · timestamp · device_id - are the primary, exact filter; the vector search only ranks within an already-correct subset.
